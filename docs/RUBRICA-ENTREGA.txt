Implementar una parte funcional del sistema dando prioridad a la calidad del código, la seguridad, la automatización mediante CI/CD y la documentación del cierre del proyecto. La entrega debe demostrar no sólo que el software funciona, sino también que fue probado, analizado y desplegado de forma reproducible.
Importante: no es necesario terminar todo el sistema planteado en el avance. Para esta entrega se evaluará principalmente un módulo funcional y verificable, acompañado de evidencia técnica suficiente.
Implementen al menos un módulo funcional del sistema. Puede ser, por ejemplo, registro y consulta de personas donantes, usuarios, citas, solicitudes, productos, pagos u otra funcionalidad equivalente de su proyecto.
El módulo deberá incluir:
- Al menos una operación de creación y una de consulta mediante interfaz web, API REST u otro mecanismo claramente demostrable.
- Autenticación con JSON Web Token (JWT).
- Al menos dos roles: ADMIN y USER, o equivalentes.
- Al menos una operación restringida exclusivamente al rol administrativo y otra disponible para usuarios autenticados.
- Validación de que un usuario sin token o sin el rol requerido no pueda acceder a las operaciones protegidas.
- La llave o secreto usado para firmar JWT no debe quedar escrito directamente en el código fuente. Utilicen variables de entorno o secretos del repositorio.
- NOTA: Para los equipos que están haciendo una aplicación móvil, agregar JWT depende de si se están cominicando con un backend. Si sí lo hacen deben agregar JWT, si no lo hacen deben justificar la ausencia de JWT y en el reporte exponer los mecanismos de autenticación/autorización que están usando.
El módulo deberá incluir pruebas unitarias automatizadas y alcanzar una cobertura mínima de 80 % sobre el código del módulo implementado.

Configuren un pipeline que se ejecute automáticamente al menos cuando se haga push o pull request hacia la rama principal del repositorio.
El pipeline deberá contener, como mínimo, estas tres etapas lógicas:
1. Pruebas: ejecutar automáticamente las pruebas unitarias.
2. Construcción: compilar, empaquetar o generar el artefacto desplegable de la aplicación.
3. Despliegue/Delivery: desplegar automáticamente la aplicación en un entorno de prueba.
Herramientas de acceso libre recomendadas:
- GitHub Actions, especialmente conveniente si el repositorio está alojado en GitHub.
- GitLab CI/CD, si el repositorio está alojado en GitLab.
- Docker y Docker Compose, opcionales pero recomendables para hacer reproducible el entorno de prueba.
Para el despliegue pueden usar cualquiera de estas alternativas:
- Un servicio que tenga un plan gratuito o académico vigente para desplegar su aplicación.
- Una máquina virtual propia o del equipo.
- Un equipo local configurado como servidor de pruebas mediante un self-hosted runner.
- Un contenedor Docker desplegado automáticamente en el entorno de prueba elegido.
- En el caso de las aplicaciones móviles el pipeline puede terminar en la generación del APK.
No se calificará una plataforma de nube específica. Se calificará que el proceso de pruebas, construcción y despliegue esté automatizado y sea demostrable.
- Archivo del pipeline dentro del repositorio, por ejemplo .github/workflows/ci-cd.yml.
- Captura o enlace a una ejecución exitosa.
- Evidencia de que las pruebas se ejecutaron antes del despliegue.
- URL, captura o instrucciones que permitan verificar el entorno de prueba desplegado.
Para alcanzar el nivel Altamente competente, las etapas de pruebas, construcción y despliegue deben ejecutarse correctamente de forma automatizada.
En esta parte se utilizarán dos tipos de análisis complementarios:
- SonarQube: analiza principalmente el código fuente para detectar problemas de calidad, mantenibilidad y seguridad.
- OWASP ZAP: analiza la aplicación mientras está ejecutándose, enviando y observando peticiones HTTP para detectar posibles problemas de seguridad.
La intención no es obtener un reporte perfecto ni corregir absolutamente todos los hallazgos, sino demostrar que el equipo sabe ejecutar las herramientas, interpretar sus resultados y corregir problemas relevantes.

SonarQube Community Build puede ejecutarse gratuitamente de forma local. Si ya tienen Docker Desktop instalado, una forma sencilla de iniciar una instancia para fines académicos es:

```bash
  -e SONAR_ES_BOOTSTRAP_CHECKS_DISABLE=true \
  -p 9000:9000 \
  sonarqube:latest

```
Después:
1. Esperen a que el contenedor termine de iniciar.
2. Abran en el navegador:
   ```text
   http://localhost:9000
   
   ```
3. Inicien sesión. En una instalación nueva las credenciales iniciales suelen ser:
   ```text
   usuario: admin
   contraseña: admin
   
   ```
4. Creen un proyecto o permitan que SonarQube lo cree al recibir el primer análisis.
5. Generen un token de análisis desde SonarQube.
6. Ejecuten el scanner correspondiente a la tecnología de su proyecto.
Documentación oficial para iniciar SonarQube Community Build con Docker:
[https://docs.sonarsource.com/sonarqube-community-build/server-installation/from-docker-image/installation-overview](https://docs.sonarsource.com/sonarqube-community-build/server-installation/from-docker-image/installation-overview)
Desde la carpeta que contiene el pom.xml pueden ejecutar primero sus pruebas y posteriormente el análisis de SonarQube.
Una forma recomendada es guardar el token en una variable de entorno llamada SONAR_TOKEN en lugar de escribirlo directamente en el repositorio.
Después pueden ejecutar:
```bash

mvn org.sonarsource.scanner.maven:sonar-maven-plugin:sonar

```
Si su configuración requiere indicar explícitamente la instancia local:
```bash
mvn org.sonarsource.scanner.maven:sonar-maven-plugin:sonar \
  -Dsonar.host.url=http://localhost:9000

```
No suban el token de SonarQube al repositorio. Si lo utilizan dentro de GitHub Actions o GitLab CI/CD, guárdenlo como secreto del repositorio.
Para otros lenguajes pueden utilizar el scanner correspondiente de SonarQube para Gradle, NPM, .NET, Python o SonarScanner CLI.
Si su proyecto es una aplicación Android, pueden utilizar SonarQube for IDE dentro de Android Studio durante el desarrollo y ejecutar el análisis global mediante Gradle + SonarScanner sobre el proyecto. Para la cobertura de pruebas pueden utilizar JaCoCo o Kover, siempre que el reporte generado pueda integrarse o documentarse junto con el análisis de SonarQube.
En este caso, la evidencia esperada es la misma que para cualquier otro proyecto: tablero general, métricas principales, hallazgos revisados y evidencia de correcciones.

OWASP ZAP es una herramienta gratuita y de código abierto para realizar pruebas dinámicas de seguridad sobre aplicaciones web y APIs.
A diferencia de SonarQube, ZAP no necesita analizar directamente el código fuente: trabaja contra una aplicación que ya está ejecutándose.
Ejemplo:
```text
                      peticiones HTTP
OWASP ZAP  --------------------------------->  Aplicación / API
           <---------------------------------
                      respuestas HTTP

```
ZAP analiza esas peticiones y respuestas y puede advertir sobre problemas como:
- posibles inyecciones SQL;
- posibles vulnerabilidades XSS;
- encabezados HTTP de seguridad ausentes;
- exposición innecesaria de información;
- cookies configuradas de forma insegura;
- respuestas o endpoints con comportamientos que requieren revisión.
Documentación y descarga oficial:
[https://www.zaproxy.org/download/](https://www.zaproxy.org/download/)
Passive Scan
ZAP observa las peticiones y respuestas que pasan por la herramienta y genera alertas sin intentar explotar activamente la aplicación. Es apropiado como primer análisis y tiene un riesgo bajo para un entorno de prueba.
Ejemplo de hallazgo:
```text
Content-Security-Policy Header Not Set

```
Active Scan
ZAP envía diferentes entradas y payloads para comprobar si la aplicación puede tener vulnerabilidades. Este análisis puede modificar datos o generar muchas peticiones.
Ejecuten un Active Scan únicamente contra su propia aplicación o un entorno de prueba para el que tengan autorización. No utilicen esta práctica contra páginas o APIs de terceros.
Para esta entrega, la forma más sencilla es utilizar la aplicación de escritorio de ZAP.
1. Inicien su aplicación o API.
   Ejemplo:
   ```text
   http://localhost:8080
   
   ```
2. Abran OWASP ZAP.
3. Seleccionen Quick Start.
4. Seleccionen Automated Scan.
5. Escriban la URL de su aplicación.
6. Ejecuten el análisis.
7. Esperen a que ZAP recorra la aplicación y termine de generar alertas.
8. Revisen la sección Alerts.
9. Seleccionen al menos un hallazgo relevante y lean:
   - nivel de riesgo;
   - descripción;
   - URL o endpoint afectado;
   - evidencia mostrada por ZAP;
   - recomendación de solución.
10. Determinen si el hallazgo representa un problema real en su proyecto o un posible falso positivo.
11. Corrijan al menos un hallazgo relevante cuando sea técnicamente razonable.
12. Ejecuten nuevamente el análisis y comparen los resultados.
Una salida típica puede contener alertas agrupadas aproximadamente así:
```text
Alerts
├── High
├── Medium
├── Low
└── Informational

```
No se calificará el proyecto por tener necesariamente cero alertas. Se calificará la capacidad de ejecutar el análisis, comprender los hallazgos y actuar sobre ellos.
Quienes ya utilicen Docker pueden ejecutar un Baseline Scan, que realiza rastreo y análisis pasivo sin efectuar un ataque activo completo.
Ejemplo:
```bash
docker run -t ghcr.io/zaproxy/zaproxy:stable \
  zap-baseline.py -t http://host.docker.internal:8080

```
En Windows y macOS, host.docker.internal permite normalmente que el contenedor acceda a una aplicación que se está ejecutando en la máquina anfitriona.
Para generar un reporte HTML pueden montar una carpeta de trabajo siguiendo la documentación oficial de ZAP:
[https://www.zaproxy.org/docs/docker/baseline-scan/](https://www.zaproxy.org/docs/docker/baseline-scan/)
Quienes tengan una API documentada mediante OpenAPI/Swagger también pueden investigar el ZAP API Scan, diseñado específicamente para APIs:
[https://www.zaproxy.org/docs/docker/api-scan/](https://www.zaproxy.org/docs/docker/api-scan/)
Esta alternativa es opcional; para cumplir la actividad es suficiente utilizar correctamente el Automated Scan de la aplicación de escritorio.
Si su aplicación utiliza JWT, es posible que algunos endpoints protegidos respondan 401 Unauthorized durante un escaneo automático. Configurar ZAP para autenticarse automáticamente con JWT es posible, pero requiere configuración adicional y no es obligatorio para esta actividad.
Para esta entrega pueden:
- escanear primero los endpoints accesibles sin autenticación;
- revisar manualmente el comportamiento de endpoints protegidos;
- documentar que determinados endpoints no fueron explorados automáticamente debido a la autenticación;
- de manera opcional, configurar autenticación en ZAP si el equipo desea profundizar.
El hecho de que un endpoint requiera autenticación no debe considerarse por sí mismo un error del escaneo.
Incluyan:
1. Captura o reporte del primer escaneo.
2. Una tabla con los hallazgos revisados, por ejemplo:
3. Evidencia del cambio realizado en el código o configuración.
4. Segundo escaneo, cuando sea posible, para mostrar el resultado después de la corrección.
5. Breve conclusión sobre los principales riesgos encontrados.
No basta con adjuntar automáticamente todos los resultados de ZAP. El equipo debe demostrar que revisó e interpretó al menos los hallazgos más importantes.
Los equipos que desarrollen una aplicación móvil Android deberán distinguir entre calidad del código, seguridad propia de la aplicación móvil y seguridad de las comunicaciones con el backend.
Una forma recomendada de organizar el análisis es:
```text
                 PROYECTO ANDROID
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
      Sonar           MobSF        OWASP ZAP
        │              │              │
 calidad código   seguridad APK   seguridad API
        │              │              │
 bugs             manifest        HTTP/HTTPS
 code smells      permisos        endpoints
 cobertura        secretos        headers/auth
 duplicación      almacenamiento  comportamiento

```
Para Android, Sonar sigue utilizándose para analizar la calidad del código fuente. Pueden trabajar con:
- SonarQube for IDE dentro de Android Studio durante el desarrollo.
- SonarScanner for Gradle para ejecutar el análisis completo del proyecto.
- JaCoCo o Kover para generar evidencia de cobertura de pruebas.
No es obligatorio que todos los hallazgos sean corregidos, pero sí deben interpretar los más relevantes y documentar las acciones tomadas.
OWASP ZAP no analiza directamente el APK. Su función en una aplicación móvil es observar y probar el tráfico HTTP/HTTPS entre la app y el backend o servicios externos.
El flujo esperado es:
```text
App Android
     │
     │ HTTP/HTTPS
     ▼
  OWASP ZAP
     │
     ▼
 Backend / API

```
Para realizar la prueba pueden:
1. Ejecutar ZAP en la computadora.
2. Configurar ZAP para escuchar en un puerto, por ejemplo 8080.
3. Configurar el emulador Android o dispositivo de prueba para utilizar la computadora como proxy HTTP/HTTPS.
4. Abrir la aplicación y recorrer sus funciones principales.
5. Verificar en ZAP las peticiones realizadas por la app, por ejemplo:
   ```text
   POST /login
   GET /users/123
   POST /donations
   PUT /profile
   
   ```
6. Revisar primero las alertas producidas por el Passive Scan.
7. Ejecutar un Active Scan únicamente contra una API propia o un entorno de pruebas autorizado.
8. Documentar los hallazgos y, cuando sea posible, corregir al menos uno y volver a probar.
Cuando la aplicación utiliza HTTPS, ZAP necesita actuar como intermediario entre la app y el servidor. Para ello puede ser necesario instalar o confiar temporalmente en el certificado de ZAP dentro del emulador o entorno de pruebas.
En Android moderno, una aplicación puede no confiar automáticamente en certificados instalados por el usuario. Para una build de desarrollo o debug puede configurarse un network_security_config que permita realizar la prueba sin afectar la configuración de producción.
Si la aplicación implementa certificate pinning, la interceptación con ZAP puede requerir cambios adicionales en la versión de pruebas. Para esta actividad no será obligatorio deshabilitar o modificar certificate pinning; el equipo deberá simplemente documentar esta limitación si aplica.
Para analizar problemas propios de Android, pueden utilizar de forma complementaria MobSF (Mobile Security Framework), una herramienta gratuita y de código abierto orientada al análisis de aplicaciones móviles.
MobSF puede ayudar a identificar, entre otros aspectos:
- permisos excesivos;
- componentes exportados incorrectamente;
- secretos o claves embebidos en el código o APK;
- configuraciones inseguras en AndroidManifest.xml;
- almacenamiento local de información sensible;
- configuraciones de red que requieren revisión.
MobSF es opcional cuando la aplicación Android consume una API y el equipo puede realizar el análisis de tráfico con ZAP.
Sin embargo, si la aplicación no utiliza backend ni comunicaciones HTTP/HTTPS, OWASP ZAP no aporta evidencia relevante. En ese caso, el equipo puede utilizar MobSF como sustituto del análisis con ZAP, siempre que explique brevemente por qué ZAP no aplica a la arquitectura de su proyecto y documente los hallazgos obtenidos con MobSF.
Los equipos con aplicación móvil deberán entregar, según corresponda:
- capturas o reporte de SonarQube;
- evidencia de cobertura con JaCoCo o Kover;
- capturas o reporte de ZAP mostrando tráfico de la aplicación hacia su backend;
- al menos un hallazgo de seguridad interpretado por el equipo;
- evidencia de una corrección o justificación cuando no sea posible corregirla;
- opcionalmente, reporte de MobSF;
- si no utilizan ZAP, una justificación técnica breve y el reporte de MobSF como evidencia alternativa.
En aplicaciones móviles, no se evaluará el uso mecánico de una herramienta específica. Se evaluará que el equipo utilice una herramienta adecuada a la arquitectura de su aplicación y pueda identificar, interpretar y corregir problemas de seguridad reales.
